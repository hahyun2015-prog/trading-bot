## 09:03 ERA 크래시(MSVCR100.dll 0xc0000417) 조사 및 임시조치 (07-13 밤)

Windows 이벤트 로그(Application, Id=1000/1001)로 확인: 07-07/07-08/07-09/07-13 4개 거래일 전부
`python.exe`가 `C:\OpenAPI\MSVCR100.dll`(키움 OpenAPI+ 번들 구버전 CRT) 안에서 동일 오프셋
(`0x0008af3e`) `0xc0000417`로 죽음. 크래시 시각은 프로세스 가동시간과 무관하게 매번 09:03:08~22초
(벽시계 시각 고정 — 우연이 아님). era_order_manager.py 로그상 항상 "키움증권 서버 통신 끊김 감지" 직후
발생. `_update_isf_direction_if_needed`(로컬 DB 조회뿐, 배제), RSA 서브프로세스(크래시 이후에만 등장,
배제), 경쟁 스케줄 작업(전체 스케줄 확인 결과 없음, 배제)까지 확인 후, 남은 유일한 용의선은
`check_connection_status()`의 `CommConnect()` 인앱 재연결 호출(era_order_manager.py:1497~) — 이미
초기화된 OCX 인스턴스에 재연결을 거는 게 크래시 방아쇠로 추정.

**적용한 임시조치**: 끊김 감지 시 기존 3회 `CommConnect()` 재시도 로직을 제거하고, 활성 거래시간대라면
즉시(1회) `schtasks /run /tn "AMATS ERA Reconnect"`로 프로세스를 통째로 재기동하도록 변경. 왜 09:03에
끊기는지(키움 서버 쪽 사정)는 로컬에서 관측 불가 — 이 조치는 "재연결 대신 하드 리셋"이라는 대증 조치이며,
**내일(07-14) 09:03 실거래에서 재발 여부로만 검증 가능**. 재발하면 이 가설도 기각하고 더 정밀한 로깅
(CommConnect 호출 전후 밀리초 단위 타임스탬프) 추가로 넘어가야 함.
