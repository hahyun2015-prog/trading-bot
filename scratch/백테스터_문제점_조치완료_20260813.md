## 1. P1 — 유령체결 방지

`realistic_gap_fill`의 기본값이 `False`라 명시하지 않으면 "봉이 목표가를 갭으로 관통해도
목표가에 체결"되는 낙관적 가정이 조용히 켜졌다. 2026-08-10 감사가 이미 지적했는데도
이틀 뒤 진단에서 또 밟았다 — 경고가 없다는 게 문제였다.

**미지정과 명시적 False를 구분하는 센티널**을 넣었다.

```python
class _GapFillUnset:      # __bool__ -> False. 동작은 기존과 100% 동일
def _resolve_gap_fill(value, func_name):
    # 미지정이면 stderr 경고 1회 (함수당). BT_STRICT_GAPFILL=1 이면 예외
```

적용 함수: `run_kalman_live_replica`, `run_chandelier_live_replica` (이 인자를 가진 전부).

**검증 — 동작 무변경**

| 함수 | 미지정 | 명시 False | 명시 True |
|---|---|---|---|
| `run_chandelier_live_replica` | 불변 (813건) | 불변 (813건) | 불변 (1,236건) |
| `run_kalman_live_replica` | 불변 (1,924건) | 불변 (1,924건) | 불변 (1,643건) |

`run_kalman_night_replica` · `run_kalman_live_replica_oc` 도 회귀 불변 확인.
경고는 함수당 1회만 출력되어 로그를 어지럽히지 않는다.

기본값을 True로 뒤집지 않은 이유는 과거 결과와의 비교가 끊기기 때문이다. 대신
**호출자가 반드시 의식적으로 고르게** 하는 쪽을 택했다. CI에서는 `BT_STRICT_GAPFILL=1`로
아예 막을 수 있다.

## 2. P5 — 하드손절의 profit_lock 종속 분리

`hard_stop_enabled=True` + `hard_stop_pt` 6~20pt를 넣어도 결과가 **소수점까지 동일**했다.
하드손절 분기가 `if profit_lock_enabled:` 안에 중첩돼 있었기 때문이다.

분기 순서를 보존하면서 중첩만 풀었다.

```python
mfe = peak_price - entry_price
_be_moved = (profit_lock_enabled and profit_lock_be_move_trigger_pt is not None
             and mfe >= profit_lock_be_move_trigger_pt)
if _be_moved:        pl_floor = ...
elif hard_stop_enabled:   pl_floor = entry_price -/+ _hs      # ← 더 이상 종속되지 않음
if profit_lock_enabled and mfe >= profit_lock_trigger_pt: ...
```

**검증 — 기존 조합 전부 불변**

| 조합 | 불변 |
|---|---|
| 현행 (둘 다 OFF) | ✅ |
| profit_lock ON | ✅ |
| profit_lock ON + 하드손절 8pt | ✅ |
| profit_lock ON + 하드손절 se_mult | ✅ |
| 낙관 기본값 (gap_fill=False) | ✅ |

**이제 단독으로 동작한다** (전 기간, `realistic_gap_fill=True`)

| 하드손절 | 거래 | 승률 | PF | 총손익 | 최악손실 |
|---|---:|---:|---:|---:|---:|
| OFF (현행) | 1,236 | 44.90% | 1.10 | +227.0pt | **-29.22pt** |
| 8pt | 1,246 | 43.90% | **1.17** | **+365.1pt** | **-8.24pt** |
| 10pt | 1,245 | 44.10% | 1.11 | +242.9pt | -10.24pt |
| 15pt | 1,244 | 44.61% | 1.06 | +148.8pt | -15.24pt |

최악손실이 -29.22 → -8.24pt로 잡히면서 PF도 소폭 개선된다.
대기 중이던 **"손절 캡" 판단을 이제 백테스트로 평가할 수 있다.**

### ⚠️ 라이브는 여전히 같은 구조다

`era/era_order_manager.py` `_apply_profit_lock()` 첫 줄:

```python
if not getattr(self, "futures_profit_lock_enabled", False):
    return dist, None      # ← 하드손절까지 도달하지 못함
```

이번 범위 밖(수정 금지)이라 **건드리지 않았다.** 따라서 현재 라이브 config
(`profit_lock_enabled: False`, `hard_stop_enabled: False`)에서는

> **config에서 `hard_stop_enabled`만 True로 켜도 아무 일도 일어나지 않는다.
> `sl_hard_cap_pt: 10.0`도 이 경로에서는 쓰이지 않는다.**

손절 캡을 실제로 적용하려면 라이브 코드 수정이 필요하며, 이는 별도 승인 사항이다.

## 3. P3 — pt 기준 지표 추가

계약수가 사실상 1계약 고정인데 자본만 불어나는 구조라 `profit_pct`·`mdd`가 왜곡됐다
(전체기간 MDD 0.58%가 분기별 MDD 1.2~5.1%보다 작게 나오는 모순).

기존 키는 그대로 두고 `total_pnl_pt`(1계약당 누적 pt)와 `mdd_pt`(그 최대낙폭)를 추가했다.
이미 있던 `pt_equiv`(거래별 계약수로 나눈 pt 환산)를 재사용해 dynamic_sizing에서도 정확하다.

| 가정 | 기존 지표 | 신규 지표 |
|---|---|---|
| 낙관 | 수익률 +4185.93% / MDD 0.58% | 누적 +8,371.9pt / 최대낙폭 32.7pt |
| 정직 | 수익률 +113.50% / MDD 75.43% | 누적 +227.0pt / **최대낙폭 153.0pt** |

정직한 가정에서 **번 것의 67%를 한 번에 반납**한 적이 있다는 게 이제 한눈에 보인다.
기존 키 전부 불변 확인.

## 5. 조치하지 않은 것과 이유

**P2 (정직한 가정도 실제보다 낙관적).** 실제 PF 0.63 < 정직 백테스트 1.79다.
`realistic_gap_fill=True`조차 현실보다 후하다는 뜻인데, 원인을 특정하려면 TCA 체결 로그와
백테스트 체결가를 1:1로 맞춰봐야 한다. 추측으로 모델을 고치면 또 다른 왜곡을 넣게 된다.

**P4 (파라미터 튜닝).** 코드 문제가 아니라 작업 방침이다. 정직한 가정에서 모든 스윕이
PF 1.0±0.2 안에 있어 지금 최적값을 고르는 건 과적합이다.

**P6 (되돌림 폭).** ATR14 기반 dist가 지연 지표라 크게 유지되는 문제. 손볼 여지는 있으나
P4와 같은 이유로 체결 모델 정합이 먼저다.

**라이브 코드.** `era/era_order_manager.py`는 열어서 확인만 하고 수정하지 않았다.
